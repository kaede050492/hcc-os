# HCC OS 再構築計画

調査日: 2026-09-30

## 現状の調査

稼働中の起動経路は `/startup.lua` → `/.hccos/system/core/bootstrap.lua` → `system/ui/desktop.lua` です。85個の追跡ファイルを持ち、22個のアプリパッケージ、インストーラー、更新・リカバリ、PNG/JPEG/QOI処理を含みます。3,537行の `hccos_v1.3.3.lua` は現行マニフェストにも起動経路にも含まれない旧版ファイルです。移行用途を確認するまでは削除せず、ランタイムから分離した履歴資産として保持します。

アプリは次の機能群に分かれています。

- 基本操作: Files、Terminal、Notepad、Image Viewer、Web、Clock、Calendar
- 周辺機器・ワールド: Player Radar、Inventory、Peripherals、Network、Resource、Server、Currency
- OS管理: Settings、System Monitor、Task Manager、Performance、Logs、Diagnostics、Updates、Setup

再利用するものはコード量ではなく、公開された動作です。アプリのマニフェストとコールバック契約、画像デコーダ、QOIライブラリ、更新・復旧処理、幾何計算、キャンバスの保持描画を監査し、責務を切り分けて必要な形で接続します。アプリを新しいOSへ大量コピーすることはしません。

| 既存部分 | 方針 |
| --- | --- |
| `system/core/config.lua`、`logger.lua` | ユーザーデータ契約を保ち、復旧可能な保存と追記ログへ再実装する。 |
| `gpu_toms.lua`、入力、ウィンドウ、コンポジター | UI向け公開契約を保ち、能力検出・論理座標・状態遷移を分けて再設計する。 |
| 画像デコーダ、QOIライブラリ、幾何、キャンバス | 既存の機能を監査し、必要部分をアダプター経由で再利用する。壁紙の読込・変換・描画コマンド生成は協調スケジューリングへ移す。 |
| 22個のアプリパッケージ | マニフェストとコールバック契約を移行用互換層で保ち、障害隔離と設定を順次移す。 |
| `_G.HCCV14/15`相当の互換名 | GUIアプリ環境から撤去し、更新処理とUI操作はウィンドウごとのサービスコンテキストから渡す。 |
| `hccos_v1.3.3.lua` | 実行経路から外した旧版資産として保管する。既存アプリからの依存がないことを確認するまで削除しない。 |
| インストーラー、更新、Recovery | 起動とロールバックを守る境界として維持し、マニフェスト容量・異常系を検証しながら改善する。 |

最初のレビューで確認した設計上の問題:

- ファイル分割はされているものの、デスクトップ各層が共有環境テーブル `E` を介して `OS`、`Driver`、`cfg` などへ直接アクセスしています。更新APIも `_G.HCCV14/15` に置かれています。
- Tom's GPUが見つからない場合、10秒待ったあとRecoveryへ移ります。Recoveryには診断・修復とCraftOSシェルがあるため修復手段はありますが、通常のデスクトップUIを標準端末へ縮退させる機能はありません。
- 描画と入力は検出したGPUのサイズをそのまま座標として使い、仕様の576×320論理画面とレターボックス変換を実装していません。
- 再描画タイマーは50ms固定で、要求される60〜10fps適応制御やアイドル時の完全な待機とは異なります。
- 設定を現行ファイルへ直接書き込み、破損時のバックアップ復元・原子的な置き換えがありません。
- ロガーは記録ごとに既存ログを全件読み、上限までの全行を書き戻します。
- 画面レイアウトと初期色は仕様書が求める576×320のFluent風UIになっていません。

## 今回の再構築作業

最初の作業単位として、OS全体を一度に入れ替えるのではなく、起動と復旧の境界を維持しながら次の責務を分離・接続しました。

- Configにサイズ上限、現行/前回/バックアップの読込、壊れた設定の退避、テンポラリファイルからの置換保存を追加しました。設定とバックアップは保存前に読戻し検証し、ファイル存在確認のAPI例外を「不存在」と誤認して置換を進めないようにしました。
- 設定ファイルの既知数値項目でもNaN・無限大・過大値を拒否し、安全な既定値を残すようにしました。
- Loggerをメモリリングと追記書込へ変更し、読取失敗時に既存ログを切り詰めないようにしました。
- Capability RegistryとPerformance Controllerを追加し、両方をOSインスタンスの起動コンテキストから渡します。
- アプリレジストリはマニフェストで宣言したエントリファイルを検査して読み込み、固定名`app.lua`以外の安全なエントリも扱います。欠落・不正なエントリは他アプリの登録を妨げず、診断に残します。代替エントリ、欠落、パストラバーサルの回帰ケースは`tests/app_registry_spec.lua`と`tests/app_manager_spec.lua`で実行します。
- OS領域を保護するFile Serviceを追加しました。Filesの削除、Notepadの読書き、Image ViewerとWebの画像・ダウンロード保存でパス・親ディレクトリ・サイズを検査し、一時ファイルを4KiB単位で照合してから置換します。削除時も未完了保存の復旧を確認し、削除をサービス経由に集約して復旧用バックアップから削除済みファイルが再出現する経路を防ぎます。Currencyの辞書とバックアップも同じ原子的保存を使い、一般ファイル操作からは管理データを変更できないようにしました。保存中断時は元ファイルを復元し、設定、起動、インストール、更新バックアップ、ログ、キャッシュ領域を一般アプリから変更できないようにしました。
- CurrencyのCSVは引用符とカンマを処理し、読込サイズ・アイテム数・コイン数を制限します。価格と数量の積がLua数値の安全な整数範囲を超える場合は結果を表示しないようにしました。
- CC:Tの`os.startTimer`は50ms刻みへ丸めるため、20TPS時のタイマー駆動描画上限は20fpsです。サーバー負荷時の実効値はさらに下がります。設定上限60fpsは希望値として保存しつつ、実効ターゲットは20fpsへ制限しました。15fpsは1/1/2 tickの配分、10fpsは2 tick間隔で生成し、実測値とタイマー上限をPerformance画面に表示します。[CC:T os.startTimer](https://tweaked.cc/module/os.html#v:startTimer)
- 15fps・10fpsの品質段階は表示状態だけにせず、CPU描画の画像サンプリングを2倍・4倍のセルへ切り替え、カレンダーの月送りアニメーションを省略します。品質段階が変わると一度だけ全画面を再構築し、壁紙はデコード済み画素を使って描画コマンドだけ作り直します。ネイティブGPU画像と通常fpsでは既存の高品質描画を保ちます。
- GPU Driverへ576×320を基準とした論理座標、設定可能な1倍・2倍表示、アスペクト比を保つ中央配置、マウス座標逆変換を実装しました。スケール変更時は全ウィンドウを新しい作業領域へ収め直し、スタートメニューも利用可能領域に合わせます。GPUネイティブ画像描画を任意機能として扱い、表示倍率・表示領域の制約や描画APIの失敗をアプリへ一度だけ通知して、Image ViewerとWebは保持中のPNGから協調的な純Lua描画へ切り替えます。
- ウィンドウ、タスクバー、スタートメニューは共有Geometryの角丸行範囲で描画とマウスヒットテストを揃えました。ウィンドウの透明な角は背後のデスクトップまたはウィンドウへ届き、タスクバーとメニューも透明な角でクリックを受けません。ウィンドウ内の塗り、線、文字、ネイティブ画像も同じ形状でクリップします。画面上の外観と複数GPU倍率での実機確認は未実施です。
- GPUの半透明・ぼかしAPIに依存せず、壁紙のリサイズ・量子化済み画素から壁紙ジョブ完了時に固定8×6グリッドを一度採取し、その平均色を暗色UI面へ上限付きで混ぜます。フレームごとの画像走査はしません。壁紙解除・読み込み失敗時は色味を戻します。近似色の実機での見え方は未確認です。
- ウィンドウの最小高さをコンパクト画面の操作領域に合わせ、2倍表示で更新・画像・Web・通貨・ネットワーク・リソース・サーバー・システム監視が主要操作を画面内に保てるようにしました。狭い幅では通貨入力キーと画像/Web操作列を再配置し、カレンダーは6週分を表示する専用レイアウトへ切り替えます。
- 実行中にGPUの必須描画APIが失敗した場合も、接続中のTom'sキーボードを標準CraftOSイベントへ切り替え、端末診断・Recovery操作に使える入力経路を残します。
- ウィンドウごとのアプリコンテキスト、異常終了後の閉じる操作、最小化/復帰の通知を整理しました。
- メニュー、コンテキストメニュー、通知、モーダルについて旧領域と新しい表示領域の両方を無効化し、最初の表示が画面全体の再描画に依存しないようにしました。
- 検索付きスタートメニュー、現在のセッションで最近フォーカスした4アプリの専用表示、起動数で時計と重ならないタスクボタン領域、タスクのページ移動を実装しました。周辺機器要件を満たさないアプリはデスクトップとスタートメニューでオフライン表示し、開いた場合の個別診断はアプリ側で行います。
- 壁紙の表示状態、画像表示モード、単色背景、UIスケール、FPS範囲と適応制御を設定画面へつなぎました。
- PNG/JPEG/QOI/HCCI壁紙の読み込みと変換・描画コマンド生成を、描画フレーム外の協調ジョブへ移しました。未設定・不正画像は単色表示へ縮退し、設定画面に最後の失敗情報を示します。同梱QOIデコーダは進捗コールバックを受け取り、プロセス全体に共有されていた画素状態をデコード単位へ移しました。
- 表示中の壁紙コマンドを保持し、デスクトップ再構築のたびに変換ジョブを繰り返さないようにしました。壁紙切替時には古いGPUネイティブ画像も解放します。
- 高密度画像が描画コマンド上限を超えた場合は部分描画を破棄し、解像度を下げて画像全体を上限内で再描画します。縮小時は診断ログへ一度だけ記録します。
- 緊急終了キーをモーダルより優先し、設定画面から有効にできる入力ルーティング診断を追加しました。任意GPUの能力照会例外もデバイス単位で捕捉します。
- アプリのタイマーをウィンドウ所有のスケジューラーサービスへ移し、最小化・異常終了・閉じる・終了時に解除するようにしました。OSタイマーはイベントルーティングから分離し、Radarの検出呼び出しを停止・再開可能にしました。アプリ例外時は所有タイマーとHTTP要求を解除した後、アプリ固有の`close`を一度だけ保護付きで実行します。
- アプリの失敗遷移をウィンドウ管理側の共通監督処理へ集約しました。アプリコールバック例外とアプリ更新タイマーの作成失敗が同じ順序でタイマー・HTTP要求・アプリ資源を解放し、ログとクラッシュ表示を一度だけ更新します。
- ダイアログの初期入力値は明示的な分岐で保持し、確認モーダルへ文字列`"nil"`が誤って入ってしまうLuaの`and/or`式の問題を取り除きました。Tom's GPUアダプターの検出結果も、検出成功時にエラー文字列を返さないようにしました。
- 共通Widgetから空の代替アクションを除きました。表示専用要素はポインター入力を消費せず、操作要素には明示的なコールバックを要求します。アプリコンテキストの`window`へヒット領域を登録し、タブごとの選択番号を固定して、クリック位置をスライダーへ渡します。ドロップダウンの表示部分は選択操作を先取りしません。
- ネイティブ画像を含む描画コマンドへウィンドウ所有者を記録し、描画障害通知はGPUコマンド列を処理した後に配送します。対応アプリは元PNGを一度だけソフトウェア変換し、描画APIがない環境やウィンドウサイズ変更でも画像表示を維持します。任意のネイティブ描画API障害ではGPU全体を停止させず、機能の再試行もデバイス再走査まで抑止します。
- 最小化からの復帰と周辺機器再走査でアプリ更新の基準時刻を再設定し、停止中の時間が`update(dt)`へ混入しないようにしました。
- GPU検出タイムアウトからRecoveryへ移る前に、ブート待機で作成した再試行タイマーを解除します。
- `core/http_service.lua`をOS所有のHTTPサービスとして追加し、Web/Image ViewerとUpdaterの非同期要求をURL単位の台帳へ登録して要求元だけへ配送します。キャンセル要求は応答が届くまで占有記録として残し、同一URLの同時要求を拒否して遅延応答の誤配送を防ぎます。デスクトップ・Recovery間でも同じサービスを使います。Webの画像応答はサイズ判定前にジョブへ所有させ、Content-Length超過経路で応答ハンドルを解放します。
- RecoveryのRepair/Reinstallが非同期HTTP応答を受け取らずUpdaterを連続実行するため、CPUを使い切って完了できない問題を修正しました。Recoveryは応答イベントを待機し、HTTPハンドルを閉じ、`C`またはCtrl+Tで更新を中止できるようにしました。Recoveryメニュー待機中も残っているHTTP応答を処理します。
- スタートメニューへ再起動・OS終了・デスクトップ表示の電源項目を追加し、CraftOSの再起動APIが利用できる場合のみ保存とウィンドウ終了の後に再起動します。検索対象はアプリ名と説明に限定し、検索欄が電源メニューを通じて背後のアプリへ文字入力を漏らさないようにしました。
- Tom's Peripheralsキーボードの`shutdown`・`reboot`イベントを確認ダイアログ付きで処理し、アプリ終了と設定保存を通ってからコンピューターを停止・再起動します。
- Player Detectorの種類名だけではPlayer Radarを対応扱いせず、アプリが使うプレイヤー一覧APIと座標取得APIの組合せを能力レジストリで判定します。座標取得はAdvanced Peripherals 0.7系で公開される`getPlayerPos`と`getPlayer`を扱い、無指定時は複数接続中の対応デバイスを優先します。[Player Detector 0.7 API](https://docs.advanced-peripherals.de/0.7/peripherals/player_detector/)
- TerminalとUpdate画面からのRecovery遷移は、起動スクリプトを重ねて実行せず、確認後に現行デスクトップを終了してBootstrapのRecoveryへ引き渡します。未保存文書がある場合は破棄されることを確認します。
- GPU未接続・初期化失敗中はTom'sキーボードをCraftOS標準イベントへ切り替え、GPU再検出待ちとRecoveryでも端末入力を受け取れるようにしました。GPUが利用可能な場合は専用イベントへ戻します。
- ウィンドウのタイトルバー全体がタスクバーより上に残るよう配置境界を調整しました。
- ウィンドウのドラッグ・リサイズ中に旧矩形だけが無効化される問題を修正し、変更後の矩形も各ポインターイベントで再描画するようにしました。
- Setup、Settings、Terminal、Updatesから`HCCV14/15`別名への依存を除去し、更新サービスとUI操作をウィンドウ単位のアプリコンテキスト経由にしました。UpdatesのAPI・環境参照をモジュール共有フィールドから外しました。

基盤再設計とホスト検証は進行中です。`docs/spec-audit.md`に受け入れ条件ごとの証拠を記録しています。現在はLua 5.2文法で107ファイルの解析に成功し、22個すべてのアプリパッケージ読込・登録と空状態での`init`/`interval`/`update`/`draw`、デスクトップ正常終了・失敗・Recovery要求時の後始末、UIオーバーレイ境界とタスクバー溢れ、イベント待ち/タイマー所有権、画像API公開と出力上限、起動失敗からRecoveryへの移行確認を含む18ホスト回帰スイートがFengariで通っています。描画確認はキャンバスモックであり、実画面の視覚品質を示しません。モジュール読込、アプリ登録・管理、ファイル/HTTPサービス、能力検出、性能制御、設定、ウィンドウ、入力、色、テーマをカバーします。これはCraftOS実行環境との同等性を示すものではありません。アプリ描画の全状態、実画像コーパス、すべての異常系、長時間運転、実機描画・入力、実MOD APIは未検証です。ローカルにネイティブLua/luac実行環境がないため、CraftOS/Tom's Peripherals上でしか確認できない条件は未検証として扱います。

入力として提供された `CLAUDE_SPEC.md` は作業開始時点で未追跡ファイルでした。要件資料として読み取り、変更せずに保持します。

## 目標アーキテクチャ

```text
最小ブート / リカバリ境界
  └─ OSインスタンス
      ├─ ロガー / バージョン付き設定ストア
      ├─ 能力レジストリ / 表示・入力アダプター
      ├─ 単一イベントポンプ / 所有者付きタイマー
      ├─ アプリレジストリ / 障害を隔離するアプリ監督
      ├─ ウィンドウ・フォーカス管理 / 入力ルーター
      ├─ 576×320論理画面 / 保持描画コンポジター
      ├─ パフォーマンス制御 / 診断サービス
      └─ デスクトップ・タスクバー・スタート・壁紙・アプリ画面
```

OSインスタンスがサービスを所有し、依存関係をコンストラクター経由で渡します。CC:Tのイベントを消費するのは単一ポンプだけです。画面描画、アプリ更新、ネットワーク完了はイベントまたは所有者付きタイマーで実行し、閉じた・最小化されたアプリのタイマーは解除します。GPUや周辺機器APIは能力検出後にアダプター越しで呼び出し、失敗はそのデバイスまたは対象ウィンドウ内へ閉じ込めます。

アプリモジュールはパッケージごとに一度読み込み、登録テーブルを共有メソッドとメタデータとして使います。ウィンドウを開くたびに個別のアプリ状態テーブル、アプリコンテキスト、タイマー・HTTP所有権を作るため、Notepadの複数ウィンドウを含めて実行状態はウィンドウごとに分かれます。共有テーブルへ実行状態を置かないことを、この登録契約の不変条件とします。

UIは常に576×320でレイアウトし、物理画面との倍率・余白・入力座標変換は表示アダプターだけが扱います。GPUが利用できない場合は、動作していないGUIを装うのではなく、CraftOS端末で診断・修復できる状態へ縮退します。

設定は既存形式を移行し、未知の単純な値は保持します。書き込み時は一時ファイルを完成させてから切り替え、前の有効ファイルをバックアップします。ログは上限付きメモリリングと追記ファイルを使い、定期的にリング内容へ整理します。アプリの公開契約は移行期間中維持し、互換層もOSインスタンスごとに閉じます。

## 実装順序

1. **基盤** — 起動経路を固定し、設定・ログ・モジュール読込・状態所有者を安定させる。既存のユーザーデータ、Setup、Recoveryを守る。
2. **表示・UI・ウィンドウ・入力** — 能力駆動のアダプター、論理座標、テーマ、デスクトップ、入力優先順位、フォーカス、モーダル、ウィンドウ遷移を実装する。
3. **システムサービス** — タイマー、HTTP応答、周辺機器検出、診断、FPS・フレーム時間を個別サービスへ分ける。
4. **標準アプリ** — 既存マニフェスト契約を保ちながらアプリ状態、ファイル検査、非同期ネットワーク、終了処理を移行する。
5. **設定・永続化** — 旧設定の移行、壁紙の有効状態・パス・表示モード・背景色、再起動復元、破損時の復旧を完成させる。
6. **障害処理・性能** — 描画とアプリ例外の隔離、タイマー解放、ダメージ領域、60/45/30/20/15/10fps制御、キャッシュとログ上限を仕上げる。
7. **検証** — 全配布Luaの構文、マニフェスト参照、設定の読み書き、アプリ契約、CraftOS互換の基本操作を確認する。Minecraft/Tom's Peripherals実機で試せない項目は未検証と記録する。

## 完了基準

各段階で前段の起動・修復手段を残します。実装段階の完了はその段階の検査が通った場合だけとし、MinecraftやGPUがない環境で実機要件を確認済みとは扱いません。設定の移行や旧ファイルの削除、配布バージョン変更は、起動と復旧の回帰確認を終えるまで行いません。

要求事項ごとの実装証拠と未検証項目は[仕様適合監査](spec-audit.md)に記録します。
